# CorvinOS v0.6: Operator Modeling

**Release Cycle:** 8 weeks  
**Target:** 2026-09-15  
**Status:** Design Phase

---

## Overview

v0.6 introduces **operator style fingerprinting** and **predictive task guidance**. The system learns *how* an operator works—their risk tolerance, speed preferences, communication style, and task strengths—then uses that model to anticipate needs and tailor suggestions.

### Five Core Ideas

#### **Idea 1: Operator Style Fingerprinting**

**Problem:** CorvinOS has no model of who it's working with. Every operator is treated identically, despite massive variation in:
- Risk tolerance (cautious vs. aggressive)
- Speed preference (thorough vs. quick)
- Communication style (formal vs. casual)
- Domain expertise (novice, competent, expert)

**Solution:** Infer a 4-dimensional operator fingerprint from decision history:

```
fingerprint = {
  risk_tolerance: [0.0 .. 1.0],      # cautious → aggressive
  speed_preference: [0.0 .. 1.0],     # thorough → quick
  communication_style: [0.0 .. 1.0],  # formal → casual
  expertise_profile: {
    task_type_id: [0.0 .. 1.0],       # per-task domain competence
    ...
  }
}
```

**Measurement:** Extract from operator decisions:
- Risk tolerance: `(times_chose_bold_option) / (bold_options_available)`
- Speed preference: `(avg_decision_time) / (baseline_decision_time)` (inverted)
- Communication style: inferred from feedback annotations (formal language → higher score)
- Expertise: `(success_rate_on_task_type)` per task type, smoothed with Bayesian prior

**Success Metric:** Fingerprint stable within ±0.1 after 50 decisions per dimension.

---

#### **Idea 2: Task Affinity Learning**

**Problem:** Some operators excel at authentication bugs but struggle with UI timing issues. CorvinOS has no way to know.

**Solution:** Measure per-task-type accuracy and build affinity confidence intervals:

```
affinity_model = {
  task_type_id: {
    success_rate: 0.87,           # 87% accurate decisions on this type
    confidence: 0.72,             # high confidence (n=35 samples)
    strength_tier: "strong",      # strong / neutral / weak
    last_practiced: timestamp,
    domain_boundary: "authentication",
  },
  ...
}
```

**Measurement:** Bayesian update on every turn outcome (success/failure/unclear):
```
P(operator_good_at_task_type) = success_count / (success_count + failure_count)
confidence = min(1.0, sample_count / 30.0)  # 30 samples = 95% CI
```

**Success Metric:** Affinity predictions >70% accurate (compared to operator's actual success rates on new unseen tasks).

---

#### **Idea 3: Decision Audit → Preference Inference**

**Problem:** Why did the operator choose option A over B? CorvinOS has no way to understand preference drivers.

**Solution:** When an operator makes a choice, capture:
1. **All options presented** (the choice set)
2. **The chosen option**
3. **Why they chose it** (free-form annotation or multi-choice reason)

Then infer preference patterns:

```
preference_model = {
  "prefers_deterministic": 0.82,       # strongly prefers predictable solutions
  "risk_averse": 0.71,                 # avoids high-variance options
  "communication_formality": 0.65,     # moderately formal
  "speed_over_completeness": 0.34,     # slight preference for thoroughness
  "tool_trust": {
    "claude_api": 0.88,                # high trust in Claude API calls
    "external_sql": 0.42,              # low trust in external databases
    ...
  }
}
```

**Measurement:** Bayesian network over choice features:
- Option complexity
- Risk profile
- Time to execute
- External dependencies
- Tool trustworthiness

**Success Metric:** Preference model predicts operator's choice >60% of the time on novel option sets.

---

#### **Idea 4: Predictive Task Suggestion**

**Problem:** Operators context-switch constantly. CorvinOS could anticipate the next task.

**Solution:** Build a time-series model that predicts task type at t+1:

```
next_task_predictor = {
  model: ARIMA(p=2, d=1, q=1),
  features: [
    last_5_task_types,
    time_of_day,
    day_of_week,
    task_sequence_pattern,
    operator_expertise_match,
  ],
  predictions: [
    {"task_type": "auth", "confidence": 0.72},
    {"task_type": "memory", "confidence": 0.18},
    {"task_type": "schema", "confidence": 0.10},
  ]
}
```

**Triggering heuristics:**
- Suggest when confidence >0.65
- Suggest only if expertise affinity is neutral-to-strong
- Suppress if operator just completed same type (avoid repetition)
- Show top 2 predictions, not more

**Success Metric:** Suggestion acceptance rate >60% (operator starts suggested task within 1 turn).

---

#### **Idea 5: What-If Replay for Counterfactual Learning**

**Problem:** Operators make decisions and want to see the outcome. But they can't easily explore counterfactuals: "What if I'd chosen option B instead?"

**Solution:** Implement **deterministic state snapshots** + **replay engine**:

1. **Snapshot state** at each decision point:
   ```
   snapshot = {
     turn_id: "turn-12345",
     decision_point: "choose_engine",
     state: {
       context: {...},
       available_options: [...],
       operator_fingerprint: {...},
       ...
     },
     cost_estimate: 0.045,
     quality_estimate: 0.87,
   }
   ```

2. **Replay logic:** Load snapshot, substitute alternative choice, re-execute:
   ```
   counterfactual = replay(snapshot, chosen_option="option_B")
   # Returns: outcome, cost, quality, side effects
   ```

3. **Counterfactual comparison UI:**
   ```
   ┌─────────────────────────────────┐
   │ What-If: Choose "Option B"?     │
   ├─────────────────────────────────┤
   │ Actual outcome (your choice):    │
   │  Quality:  87%  Cost: $0.045     │
   │                                  │
   │ What-if outcome (if you chose B):│
   │  Quality:  82%  Cost: $0.038     │
   │  Trade-off: 5% quality for 16%   │
   │            cost savings          │
   │                                  │
   │ [Learn from this]  [Try Option B]│
   └─────────────────────────────────┘
   ```

**Constraints:**
- Replay must be **deterministic** (same input = same output)
- Replay must complete in <500ms
- Snapshots stored for 30 days (then purged)
- Cost estimation must be accurate ±10%

**Success Metric:** Operators use replay >3x per week; satisfaction >4/5 on counterfactual insights.

## Success Metrics

### Fingerprinting Accuracy
- **Target:** Fingerprint stable within ±0.1 after 50 decisions per dimension
- **Measurement:** Standard deviation of estimates across 5 consecutive 10-decision windows
- **Threshold:** Pass if σ(fingerprint_estimates) < 0.1

### Affinity Prediction
- **Target:** Affinity predictions >70% accurate vs. actual operator success rates
- **Measurement:** Operator makes 10 new-type decisions; compare predicted affinity to actual success rate
- **Threshold:** MAE(predicted_affinity, actual_success_rate) < 0.15

### Suggestion Acceptance
- **Target:** >60% of suggestions accepted within 1 turn
- **Measurement:** (accepted_suggestions) / (offered_suggestions)
- **Threshold:** Pass if ratio ≥ 0.60

### What-If Replay Engagement
- **Target:** >3 replay sessions per operator per week
- **Measurement:** Count of `/api/learning/replay` calls per tenant per week
- **Threshold:** Pass if avg ≥ 3.0

### Latency Targets
- **Fingerprint inference:** <100ms (p99)
- **Task prediction:** <50ms (p99)
- **What-If replay:** <500ms (p99)
- **Threshold:** All three meet targets; any violation is a regression

### Privacy & Security
- **Zero PII leakage** into audit trail (automated check via `_assert_safe`)
- **Operator can opt-out** of fingerprinting (Settings toggle)
- **Local storage only** (no server sync without explicit consent)
- **Threshold:** Pass security review with zero HIGH findings

## Integration with v0.5

### Backwards Compatibility
- v0.5 operators upgrade automatically (no action required)
- Fingerprinting starts immediately (non-intrusive)
- Suggestions are additive (opt-in via Settings)
- Decision audit is transparent (recorded but not visible unless operator enables it)

### Data Migration
- Existing v0.5 decisions *not* backfilled into fingerprint model
- Model builds forward from v0.6 deployment
- Fingerprint available 1 week post-deployment (50+ decisions threshold)

### Feature Flags
- `operator_modeling_fingerprinting` (default: ON) — infer operator fingerprint
- `operator_modeling_suggestions` (default: OFF) — show predictive suggestions
- `operator_modeling_replay` (default: OFF) — enable What-If replay
- `operator_modeling_telemetry` (default: ON) — track acceptance rates, latency (no PII)

## GDPR Compliance Notes

**Art. 5 (Lawfulness):** Operator model inference is based on lawful processing of operator's own decisions (their own data, Art. 6(1)(a) consent via bot disclosure). No third-party enrichment.

**Art. 6 (Legal Basis):** Fingerprinting is an operational necessity for personalized guidance (Art. 6(1)(b) contract fulfillment) + operator's explicit consent (Art. 6(1)(a) via disclosure card + Settings opt-out).

**Art. 30/32 (Records & Security):** All fingerprint data stored locally (no transmission), encrypted at rest, hash-chained in audit trail. Audit records include `operator_fingerprint` changes with timestamp.

**Art. 17 (Right to Erasure):** Operator can request deletion of fingerprint. Trigger purges all decision history + fingerprint state; model reverts to blank slate. Data erasure is immediate and verified.

**Data Minimization:** Only collect:
- Decision choices (which option was selected)
- Decision outcomes (did it work)
- Operator annotations (free-form reason, ≤200 chars)
- Aggregate metrics (risk tolerance, speed, affinity)

Never collect: prompt content, response content, conversation history, user data from turns.

## Risk Assessment

| Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|
| **Fingerprint inaccuracy misleads operator** | Medium | High | Calibration phase (Phase 4), operator can disable in Settings, accuracy benchmarks before release |
| **Prediction model overfits to seasonal patterns** | Medium | Low | ARIMA + cross-validation, seasonal decomposition, human-in-loop override |
| **What-If replay has side effects (unrolled transactions)** | Low | High | Dry-run snapshots, state isolation, audit trail of all replays, rollback on error |
| **Privacy leak: fingerprint data exposed in logs** | Low | High | `_assert_safe` validation on all exports, PII scrubbing, encrypt at rest |
| **Operator disables all features, model atrophies** | Medium | Low | Graceful degradation (all features optional), null-model baseline |
| **Latency regression on high-traffic tenants** | Medium | Medium | Performance budgets per Phase 4, p99 monitoring, async inference where possible |

## Rollback Procedure

**If v0.6 is unstable:**

1. **Disable learning flags** (Ops decision):
   ```yaml
   spec.features.operator_modeling_fingerprinting: false
   spec.features.operator_modeling_suggestions: false
   spec.features.operator_modeling_replay: false
   ```

2. **Drop fingerprint data** (if needed):
   ```bash
   DELETE FROM operator_fingerprints WHERE tenant_id = '*';
   DELETE FROM audit_trail WHERE event_type IN (
     'operator_fingerprint_updated', 'suggestion_offered', ...
   );
   ```

3. **Restore v0.5 behavior:**
   - Console shows no suggestions
   - No What-If replay available
   - Audit trail cleaned of decision audit events
   - Operator experience unchanged

4. **Timeline:** Rollback <5 minutes (flags are instant), data cleanup <30 minutes
